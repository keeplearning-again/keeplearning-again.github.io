# Repo Management

帮助团队让仓库中的工作有清楚的目标、边界、完成证据和续接入口。根据项目规模与风险选择最轻的有效做法，不把某个仓库的工具或步骤编号当作通用规定。

## 先了解现状

阅读仓库现有的 README、贡献说明、任务记录、CI、发布流程和适用的本地规则；查看 Git 状态及相关运行或发布记录。区分已经执行的流程、只写在文档里的约定，以及仍待决定的事项。现有流程能满足目标时，沿用它。

## 工作原则

1. **任务有可验证的终点。** 为重要任务写明目标、交付物、验收条件、状态和证据位置。把「已实现」「已验证」「已集成或发布」分开；只有达到该任务约定的终点才标完成。阻碍要写清解除条件和下一步。
2. **变更与运行有稳定边界。** 让每项并行工作能定位到分支或提交；多人并行、长任务或高风险改动可使用独立 worktree。正式构建、部署或长时间运行应记录固定提交和配置，避免进行中的编辑悄悄改变结果。集成前核对最新状态并处理冲突，不覆盖他人的工作。
3. **规则落到可执行检查。** 优先为泄露密钥、误提交大产物、依赖漂移和关键接口破坏等真实风险设置忽略规则、提交检查或 CI。人工评审负责自动检查难以判断的语义、设计和用户需求。检查强度随影响范围增加。
4. **输出能追溯输入。** 对重要运行或发布，保存代码版本、依赖、输入或数据版本、配置、输出身份和验证结果。区分源码、可共享配置、本机秘密与生成产物；不要用同名覆盖已发布结果。缓存和断点续跑要核对来源，防止旧结果冒充新结果。
5. **验证结论写明范围。** 按风险选择检查；跨组件或运行链路变更可先做小规模端到端验证，正式验收仍按目标场景进行。记录测试命令、环境、通过与跳过项、未覆盖范围；高风险改动争取独立复核及失败路径检查。smoke 成功不代表正式质量达标。
6. **交接以现场和证据为准。** 交接记录目标、当前状态、关键决定、未提交改动、在途作业、证据位置及下一步。接手时先核对 Git 和实际产物；发现文档过期时先报告，只有修改属于当前任务范围才更新。不重复消耗已充分验证且未变化的工作。

## 应用方式

- 用户要盘点流程时，先指出已经奏效的做法和当前最大的协作或可复现风险，再给按优先级排序的少量改进；用仓库事实支撑判断。
- 用户要建立流程时，先提供最小任务记录与完成判据，再补变更隔离、自动检查、产物追溯和交接；只创建真正会被维护的文件。
- 用户要执行具体任务时，遵守仓库已有规则，选择与风险相称的验证和记录；不要因本 skill 擅自扩展任务、推送、发布、删除产物或改变权限。

一个轻量任务记录可采用：`目标 | 交付物 | 验收条件 | 状态 | 证据 | 下一步`。字段可以合并，但完成状态必须能被证据核对。
